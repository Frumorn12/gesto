# Gesto (app Android) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Trasformare l'app Waypad in Gesto: nome, icona e tema nuovi, una home dei PC con riconnessione automatica, pairing con PIN, quattro modalità (Touchpad, Schermo, Tastiera, Comandi), testi in inglese e italiano.

**Architecture:** La rete (`core/network`, `core/video`, `core/audio`) resta com'è. Il ViewModel cambia solo dove il design lo chiede: nuovo enum `Screen`, avvio con riconnessione, avvisi (`Notice`) al posto di `ConnectionState.Error` per i comandi falliti, pairing approvato. La UI segue lo schema che c'è già: un solo raccordo (`ui/GestoBindings.kt`) traduce lo stato del ViewModel in stati e callback per schermata (`ui/state/`), e ogni schermata è una funzione pura di stato + azioni con le sue `@Preview`. La logica nuova che si può isolare (gesti, back, qualità, presenza dei PC, Wake-on-LAN, traduzione errori) va in classi pure con test JVM.

**Tech Stack:** Kotlin, Jetpack Compose (BOM 2026.02.01, material3), DataStore Preferences, JUnit 4 (test JVM in `app/src/test`), Gradle 9.7.1, AGP 9.0.0.

**Spec:** `docs/superpowers/specs/2026-11-05-gesto-redesign-design.md` (la proposta visiva è una pagina privata, non inclusa nel repository).

- Mappa di `ErrorTranslator` (codice/eccezione → stringa; in inglese/italiano):
  - `java.net.ConnectException` → `error_pc_refused` "The PC is not answering on port %1$d. Check that Gesto is running on it." / "Il PC non risponde sulla porta %1$d. Controlla che Gesto sia acceso."
  - `java.net.SocketTimeoutException` → `error_pc_timeout` "The PC took too long to answer." / "Il PC ci ha messo troppo a rispondere."
  - `java.net.NoRouteToHostException`, `UnknownHostException` → `error_pc_unreachable` "This PC can't be reached from this network." / "Da questa rete il PC non si raggiunge."

  - `GestoApiException.code`: `pairing_denied` → `error_code_wrong` ("The code is wrong or expired." / "Il codice è sbagliato o scaduto."), `rate_limited` → `error_too_many_attempts`, `public_pairing_denied` → `error_public_pairing`, `pairing_rejected` → `error_rejected_on_pc` ("Pairing was declined on the PC." / "Il collegamento è stato rifiutato sul PC."), `pairing_timeout` → `error_no_answer` ("Nobody answered on the PC." / "Nessuno ha risposto sul PC."), `approval_unavailable` → `error_approval_unavailable` ("This PC can't show the request. Use the code instead." / "Questo PC non può mostrare la richiesta. Usa il codice."), `pairing_busy` → `error_pairing_busy`, `unknown_app` → `error_unknown_app`, `unauthenticated` → `error_session_expired`
  - qualunque altro → `error_generic` con il messaggio come argomento ("Something went wrong: %1$s" / "Qualcosa non ha funzionato: %1$s").
- `ReconnectPolicy.nextDelay`: tentativi 0,1,2,3,… → 0, 1000, 2000, 3000, 3000, … ms; `null` quando `elapsedMillis + delay > budgetMillis`.
- Comportamento del ViewModel:
  - comando fallito non di trasporto → `notices.emit(Notice(ErrorTranslator.translate(e, Command)))`, `connectionState` resta `Connected`;

  - ping ogni 5 s quando collegato e senza input nell'ultimo secondo: `latencyMs` = tempo di andata e ritorno; due ping falliti di fila = errore di trasporto.
